# Architecture

This document explains how the app is structured and how the pieces fit together. It's written as a learning reference, not just technical docs.

## How React apps are structured

A React app is a tree of **components** — each one is a function that returns UI. The root is `App.tsx`, which decides which **page** to render based on state. There's no URL router here; navigation is done by changing a `currentPage` state variable.

```
App.tsx
├── Header (always visible)
├── HomePage        (when currentPage === 'home')
├── ProfilePage     (when currentPage === 'profile')
└── RoomDetail      (when currentPage === 'detail')
```

## State management

There are two kinds of state in this app:

**Local state** (`useState`) — lives inside one component and doesn't need to be shared. Example: the search text on the home page.

**Global state** (`useContext`) — needs to be accessible from many components. This app uses one context:

- `AuthContext` — holds the current user and the `signIn`/`signOut`/`signUp` functions. Any component can read from it without prop drilling.

## Data flow (Supabase)

Supabase acts as both the database and the auth provider. The `lib/supabase.ts` file creates a single client that is used throughout the app.

```
Component
  → calls supabase.from('purchases').insert(...)
  → Supabase applies Row Level Security (RLS) policies
  → Returns data or error
  → Component updates state
```

Row Level Security means each user can only read and write their own data — enforced at the database level, not in application code.

## Custom hooks

`usePurchases.ts` is a custom hook that encapsulates all purchase-related logic (fetching, buying, checking if already bought). Components just call `const { purchases, buyRoom } = usePurchases()` and get everything they need without caring about the implementation.

This is a common React pattern: extract data-fetching and business logic into hooks, keep components focused on rendering.

## TypeScript types

`src/types/index.ts` defines the app's core types:

- `EscapeRoom` — the room data shape
- `UserPurchase` — a record linking a user to a room
- `Page` — union type for valid page names (`'home' | 'profile' | 'detail'`)

`src/types/database.ts` is auto-generated by Supabase and describes the exact shape of the database tables.

## Adding a backend: two paths

When you need sensitive business logic (e.g. real payments), there are two options — choose based on complexity:

### Option A: Supabase Edge Functions (simpler)

Small TypeScript/Deno functions that run server-side inside Supabase's infrastructure. No separate deployment needed.

```
React → Supabase (auth + DB + Edge Functions) → Stripe
```

Good for: Stripe webhooks, simple payment logic, staying in one platform.

### Option B: Go API (more control)

A separate Go service handles sensitive operations. React still uses Supabase for auth and reads; Go owns writes that must be trusted.

```
React → Supabase (auth + DB reads)
React → Go API → Stripe
              └→ Supabase (DB writes via service role key)
```

Good for: learning Go, complex business logic, full control over the runtime.

**The backend choice is undecided** — Go or Edge Functions, to be decided when payments are actually built. See [STRIPE.md](./STRIPE.md) for the trade-offs and payment integration plan.

### What changes in React (either path)

Minimal — only `usePurchases.ts` changes. Instead of inserting directly into Supabase, `buyRoom` calls an API endpoint:

| Now (simulated) | Later (real payments) |
|---|---|
| `supabase.from('purchases').insert(...)` | `fetch('/api/checkout', { method: 'POST', body: ... })` |

Components don't change at all.
